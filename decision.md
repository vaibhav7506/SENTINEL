# Sentinel decision record

This file records the consequential choices in the current Sentinel implementation, why they were made, how they were checked, and what remains unproved. A passing local test is not a claim that the hosted system works. For dated commands and counts, see [Phase 2 verification](docs/phase2-verification.md), [Phase 3 verification](docs/phase3-verification.md), and [Phase 4 preparation](docs/phase4-deployment-preparation.md).

| Step | Decision and reason | Evidence and limit |
| --- | --- | --- |
| Preserve the baseline | Keep the verified telemetry, feature schema, model artifacts, threshold, training data and historical evaluation unchanged. This lets SaaS work be judged without moving the ML target. | All 78 protected hashes match. Held-out recall and F1 are still zero; the model is not proven useful for operational forecasting. |
| Add accounts before push ingestion | Browser users belong to one account and have OWNER, ADMIN or MEMBER permissions. One-time enrollment creates a server-owned host identity and a separately revocable permanent key. An agent payload cannot choose its account or host. | Local registration, role, enrollment, expiry, replay, revocation and account-switch tests passed in Phase 2. |
| Enforce tenancy twice | Application queries use account-scoped sessions; customer transactions also use PostgreSQL RLS under a non-owner role. The trusted authentication/scheduler connections retain owner access only for their required duties. | Five disposable database cohorts exercised RLS, cross-account IDs, pool reuse and schema parity. Managed Tiger Cloud role privileges still need live validation. |
| Push telemetry over outbound HTTPS | Customer hosts may be behind private networks, so the agent batches versioned samples to `POST /agent/v1/metrics`. The API authenticates the key before accepting the body, derives ownership from the key and stores samples in TimescaleDB. | A real Windows agent passed enrollment, restart, heartbeat and revoked-key checks; the local 100-host cohort inserted 2,900 synthetic samples. A hosted agent test is pending. |
| Bound and deduplicate ingestion | Limit batch and body size, accepted metric names/ranges and timestamp drift. Unique host/timestamp rows make retransmission safe. Redis atomically enforces a host-key bucket and an account bucket across API replicas; failure closes ingestion with 503. | Replay, 429/503 and two-replica rate-limit contracts passed locally. |
| Keep one global model | The verified supervised MLP and unsupervised detector operate on each host's isolated feature window. Per-account training is deferred because it would change model governance and the frozen evaluation. | The local cohort produced an actual model prediction for each of 100 hosts; 50 cross-account API probes returned 404 and a forged worker envelope was rejected before model load. This does not establish predictive accuracy. |
| Separate scheduling from requests | Celery Beat finds due active hosts; Redis carries tasks; Celery workers run on supported Python 3.13 and call a persistent Python 3.14 scoring subprocess. API handlers do not perform ML scoring. | Real Redis, Beat, worker, model scoring and a retry with duplicate suppression passed in the local cohort. The final image rebuild and latest queue metrics remain pending. |
| Make retries safe | Each prediction is keyed by account-scoped host, window end and model version. A database lease and uniqueness guard prevent duplicate scoring; alert state and delivery IDs limit repeated sends. | Held-lease RETRY then replay produced one prediction. Unknown external delivery outcomes are not called exactly-once. |
| Route only account alerts | Alert channels belong to an account; destinations are encrypted with the account bound into their ciphertext. SHAP and the optional LLM use only that account's incident evidence; LLM failure yields a deterministic summary. Remediation remains advisory and requires human approval. | Local routing, fallback and restart deduplication passed. External Slack/email and LLM services have not been accepted in production. |
| Separate customer and platform data | Customer telemetry and predictions stay in TimescaleDB. Grafana Cloud receives an allowlisted aggregate platform registry through Alloy, with no account or host labels. | Offline dashboard and allowlist checks passed; real remote write and dashboards remain pending. |
| Replace Railway with Oracle A1 | The Railway trial ended. The selected application host is Oracle Always Free Ampere A1 ARM64; Tiger Cloud remains the managed database and Grafana Cloud the platform-monitoring destination. The production Compose profile includes API, push worker, Beat, frontend, Redis and HTTPS Caddy. | ARM64 Compose and GitHub Actions configuration parse offline. Native ARM image/model CI and actual VM deployment have not run; the Oracle account and VM are not yet available. |
| Publish images only after gates | GitHub Actions must pass application, database, frontend, image scan and native ARM checks before immutable image digests are published. The operator then deploys reviewed digests and runs a controlled migration. | The SaaS branch is in a draft PR. Branch CI is distinct from gated image publication on `main`; no SaaS image digest or deployment is claimed. |
| Compare frozen ML evidence across CPUs within measured bounds | Keep two training reruns byte-identical on the same machine, exact classification outcomes, and the frozen x86 artifacts unchanged. Compare the ARM64 cutoff and calibration floats to the historical x86 report with narrow absolute tolerances because CPU math differs. | ARM64 CI measured cutoff drift of 2.4e-7 and calibration drift up to 3.1e-6. The test limits these to 1e-6 and 5e-6 respectively; native ARM CI must validate the correction. |
| Give database CI its required Redis service | The disposable SaaS and push cohorts exercise a shared Redis rate limiter and its failure handling. CI maps a dedicated Redis service to the cohort runner's `127.0.0.1:16379` endpoint. | The prior final-SHA Linux job returned 503 when no Redis service was started. The corrected job must pass remotely; no customer data is used. |
| Canonicalize the downloadable agent bundle | Git checkouts may preserve LF on Linux and expand it to CRLF on Windows. Normalize text source bytes to LF before hashing and archiving so the installer checksum and `--check` result do not depend on the build host. | The Windows CI run exposed a stale-archive comparison even though the local checkout passed. The new archive and manifest are regenerated from the same source files; Windows CI must confirm the fix. |
| Protect the live database during cutover | Migration `0008_push_pipeline` is additive, checked on disposable databases and guarded by a production backup acknowledgement. The API readiness contract requires the expected migration. No destructive downgrade is allowed. | Disposable migration/schema checks passed. The existing live database remains at `0007_saas_foundation`; preserving its original values across the live 0008 cutover is still pending. |
| Stop large local builds when storage is unstable | A worker rebuild exhausted Windows disk space and required Docker filesystem recovery. A later rebuild was stopped before its ML dependencies filled C: again. Application volumes and the private recovery backup were retained. | Docker recovered and the existing frontend/API proxy returned HTTP 200. A full final worker image and browser-level tenant dashboard acceptance are still pending. |
| Keep the stack verifier aligned with services | Adding Redis made the old nine-service smoke assertion stale. The verifier now expects the ten actual Compose services and checks the eight that define a health check. | A fresh local run passed API, frontend/proxy, Prometheus, Grafana, demo and the full service/health set. This does not verify the new push-worker image or cloud deployment. |

## Publication rule

The [public repository](https://github.com/vaibhav7506/SENTINEL) has a frozen earlier baseline on `main` through `4af3190d6fa7e306d6044ff7ee95148ccded8e6e`. Subsequent SaaS changes must be reviewed for credentials and committed in groups of three to five commits per work phase, at least five minutes apart. Commit titles and bodies describe the product change without phase-number prefixes. Do not treat a partial commit, a green unit suite, or the existence of a deployment file as Phase 3 or Phase 4 acceptance. Record the exact CI run, published digest, migration revision and tested endpoint when those events occur.
