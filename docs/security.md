# Sentinel SaaS security

The API authenticates browser sessions and permanent host credentials independently. Browser passwords use salted scrypt; opaque session tokens, CSRF tokens, enrollment tokens and permanent host keys are stored as hashes. Cookies are host scoped, HttpOnly for sessions, and Secure in production. Production uses same-origin HTTPS (`https://DOMAIN/api`) with explicit browser origins. Unsafe requests require a verified CSRF header. React renders customer strings as text.

OWNER manages team, account integrations and audit access; ADMIN manages hosts and enrollment; MEMBER reads account resources. Server permissions apply even when navigation is hidden. Account identity comes from the authenticated principal or permanent host credential. Customer-controlled payloads cannot select account_id, host_id, roles or model versions. Missing or foreign resources return 404/403.

Customer reads and writes enter a transaction under the non-owner `sentinel_app` role with transaction-local account context. PostgreSQL RLS and ownership triggers enforce account boundaries, including raw metrics and background prediction jobs. Authentication/bootstrap and trusted scheduling use the database connection owner, then switch to the restricted role for customer transactions. This is a documented trusted-service boundary: a compromised owner credential can bypass application isolation. Restrict database access to the VM, rotate owner credentials, and validate managed role privileges before launch.

Agent ingestion authenticates before reading the body. Version 1 accepts 1–120 samples, at most 128 KiB, fixed numeric metric names/ranges, timezone-aware timestamps up to 30 seconds ahead or 30 minutes behind, and no extra identity fields. Revocation is rechecked while the credential row is locked. Timestamp replay is idempotent. Redis atomically charges independent credential and shared account buckets using server time. Failure of Redis rejects ingestion with 503; limits return 429 and Retry-After. Production login/register limits share Redis across API instances. API request paths are templated before entering logs/metrics.

Integration destinations use Fernet authenticated encryption, including the owning account in the encrypted message. Ciphertext cannot be reused by another account; destinations and tokens are absent from API responses. Store the generated key privately and preserve it across redeploys. Key rotation needs a deliberate decrypt/re-encrypt migration; changing the environment value alone makes existing destinations unreadable. HTTPS destinations require an operator allowlist, redirects are disabled, and email uses STARTTLS. HTTP is allowed only for the local loopback test receiver.

Audit records are append-only, with database triggers rejecting UPDATE and DELETE. Host credentials and one-time enrollment tokens can be revoked independently. Unknown delivery outcomes remain unknown rather than being blindly retried. An interrupted send is recovered under a delivery lease. Exactly-once delivery to arbitrary external services is not claimed; receivers should honor the supplied delivery identifier.

Production chaos is rejected at startup and its public paths are blocked at the edge. RunbookOS defaults to disabled, supports mock advisory intake only, requires human approval and never executes remediation. LLM input uses facts from the current account; failed or invalid selection falls back to deterministic supplied evidence.

Only ports 80/443 are public in the Oracle profile. Redis, API, workers and Alloy use the private Compose network. Tiger Cloud requires SSL and network restrictions. Public metrics/docs/chaos routes are blocked by Caddy. Platform metrics have a fixed label/metric allowlist; customer raw telemetry remains in TimescaleDB. Secrets remain in ignored private files/environment variables, never in committed deployment examples. Live cloud security acceptance is pending account provisioning.
